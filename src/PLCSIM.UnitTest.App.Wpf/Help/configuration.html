Configuration use cases

A JSON configuration describes a repeatable UnitTest setup. Use it with Import Configuration to prefill an editable WPF session, with Load UnitTest for the WPF managed setup flow, or with the command-line application for CI execution.

This is a setup format, not a serialized WPF session. Project ownership remains an application/session decision. Runtime provisioning intent can be configured; profile-specific target addresses remain owned by the selected profile.

Minimal configuration

{
  "version": 2,
  "project": {
    "source": "path-to-project"
  },
  "accessProfile": {
    "id": "profile-id"
  }
}

This is a complete common configuration. Whether the selected profile accepts an empty profile payload depends on its own published fields, defaults, and validation.

Use schema version 2 for new configurations. An omitted runtime section means CreateOwned, which is usable only if the selected profile supports creation. For an existing runtime, supply explicit UseExisting as shown below and the target values required by that profile.

Root configuration

The root object identifies the configuration format and contains the project, access-profile, execution, and output sections described below.

JSON pathRequiredMeaning
versionYesConfiguration contract version: 2, or legacy 1 without a runtime section.
runtime.provisioningModeNoCreateOwned (default) or explicit UseExisting. Requires version 2.
projectYesProject source used to select and initialize an access profile.
accessProfileYesAccess-profile selection and profile-owned configuration.
executionNoCommon execution-policy overrides.
outputNoOutput policy for consumers that honor it.

Project source: project

Runtime provisioning is independent of project build/download. With UseExisting, the configured target must resolve, or the profile must provide a documented default. Invalid explicit targets never fall back to another runtime. An address without a provisioning mode still means CreateOwned and is rejected if it selects an existing target. To migrate an existing-target configuration, set version 2 and runtime.provisioningMode to UseExisting. Unsupported creation stops before transfer; WPF leaves the selection editable.

JSON pathRequiredMeaning
project.sourceYesProject entry point interpreted by the selected profile. This may be a project file, archive, or another source kind published by an installed profile.
project.authorization.safetyPasswordNoCLI-only credential used when the selected profile requires Safety-program authorization before managed build or transfer. WPF discards this value and asks interactively when authorization is supported and required.
Credential handling. Keep configuration files containing safetyPassword protected. The value is never written to normal output, diagnostics, evidence, configuration summaries, command-line arguments, or exported WPF state.

Access profile: accessProfile

This section selects the access profile and carries its own configuration payload. The application understands the profile identity, but it does not interpret the fields below accessProfile.values.

JSON pathRequiredMeaning
accessProfile.idYesRegistered access-profile identity.
accessProfile.versionNoExact semantic version. If omitted, the highest registered version for the id is selected.
accessProfile.valuesNoProfile-owned JSON object. Omission is treated as an empty object and is valid only when the selected profile can supply or accept all required values.

Profile-owned values

The selected profile defines the available field identifiers, value types, required fields, allowed values, defaults, inactive fields, and cross-field validation. Nested objects and field names therefore differ between profiles and may evolve independently of this common file format.

For interactive authoring, load the profile in WPF and use the fields projected in Step 3. Those editors read and update accessProfile.values through the profile configuration service. For manually authored or generated files, use docs/configuration.md in the selected deployed profile package. That profile-owned document defines its JSON paths, value types, defaults, allowed values, dependencies, and examples.

In a default installation, profile configuration documentation is located below C:\Program Files\PLCSIM.UnitTest\profiles\<profile package>\docs\configuration.md. When profile discovery is configured to use another directory, locate the same relative document below that active profile package root.

Profile boundary. Do not copy keys from another profile or assume that a binding version defines the payload. The access profile owns this schema and receives the complete values object without application-side interpretation of vendor semantics.

Compatibility and migration

Configuration schema version, access-profile API contract, component package versions, and PLC communication contracts are separate boundaries. The application accepts profile packages declaring API contract 2.0.0; API 1.0.0 packages are rejected before loading. accessProfile.version selects a component package version, not an API contract or vendor product version.

Legacy schema-1 files remain readable with implicit CreateOwned and cannot contain a runtime section. To preserve intended reuse, migrate to schema 2 with explicit UseExisting; the former RequireExisting name is not accepted. Install a compatible profile and binding composition, use its packaged configuration guide to migrate profile-owned values, and explicitly refresh registration under the execution account.

Execution timeout overrides: execution.timeouts

The optional execution.timeouts object overrides common application defaults for this configuration. Values use invariant TimeSpan text such as 00:01:00. Omitted fields retain their application defaults.

JSON pathBoundary
execution.timeouts.projectPrepareProject access and project-target preparation.
execution.timeouts.buildTransferOne combined build and transfer deadline.
execution.timeouts.runtimePrepareRuntime attachment or owned creation.
execution.timeouts.plcCommandPLC command transport/API acceptance.
execution.timeouts.plcStartReaction, execution.timeouts.plcStopReactionObserved PLC reaction after command acceptance.
execution.timeouts.communicationPrepareUnitTest communication establishment.
execution.timeouts.communicationRevalidationMaximum stale period; zero disables terminal timeout handling.
execution.timeouts.unitTestCommandRunControl command transport/API acceptance.
execution.timeouts.unitTestCommandReactionObserved RunControl reaction.
execution.timeouts.testRunActive run observation after trusted start evidence.
execution.timeouts.finalEventWait for final Event Stream evidence after terminal lifecycle evidence.

Output policy: output

JSON pathRequiredMeaning
output.directoryNoArtifact directory for consumers that use configuration-owned output policy.
output.testResultNoEnables generation of the test-result artifact for consumers that honor this field.

The WPF application uses its application artifact settings instead of these values. The CLI requires its explicit output-file argument for the JUnit artifact.

Consumer-specific behavior

  • Import Configuration creates an editable draft and does not select project ownership.
  • Load UnitTest uses application-managed project handling.
  • WPF ignores output.directory and output.testResult and uses WPF artifact settings.
  • WPF discards persisted project credentials and requests a transient password only when the selected profile reports PasswordRequired.
  • The CLI requires its explicit output argument for the JUnit file.
  • Project ownership is not a configuration-file field. Runtime provisioning intent is preserved by both import and load; importing alone does not prepare a runtime.

Configuration validation

Use check-config --file <configfile> as a lightweight preflight. It checks the common JSON shape, registration currentness, and registered profile selection. It does not load the profile, validate profile-owned values, discover operational targets, or prove project/runtime readiness.

Profile-owned validation and target resolution occur during CLI run or WPF setup progression. A successful preflight therefore does not guarantee that setup or execution will succeed. Missing or stale registration must be refreshed explicitly; neither check-config nor run repairs it automatically.
