Execution model

CI runs use the command-line application on a self-managed Windows agent. Install PLCSIM UnitTest, the selected access profile and bindings, and all required vendor products before assigning jobs to that agent. Complete vendor authorization separately and register access profiles once under the same Windows account that executes the pipeline.

Real-runtime jobs must be serialized per simulation and engineering environment. Do not allow independent jobs to control the same runtime, project, or vendor API session concurrently.

Provision the agent once

  1. Install a fixed application distribution and the required profile and binding components. The default CLI path is C:\Program Files\PLCSIM.UnitTest\PLCSIM.UnitTest.App.Cli.exe.
  2. Install and license the required vendor products and complete their permissions and authorization setup according to the selected profile's packaged documentation.
  3. Run register-profiles as the Windows account that executes the CI agent. Registration is per user, normally requires no UAC elevation, and is not performed by silent Setup.
  4. Run list-profiles and check-config under that account before assigning jobs.

Repeat the relevant checks after application, profile, or binding upgrades. Worker authorization must be renewed when its binary changes. Do not register profiles in every test job: registration changes persistent provisioning state and does not perform vendor authorization. The selected profile and binding documentation defines the applicable vendor requirements.

Pipeline flow

  1. Select output and collection paths specific to the current job/build attempt before running preflight.
  2. Use list-profiles to verify the provisioned profile registry.
  3. Use check-config --file <configuration> as the configuration preflight.
  4. Use run --file <configuration> --output <junit-file> to execute the UnitTest.
  5. Publish the JUnit file when it exists and preserve the CLI exit code as the authoritative job result.

The console output is intended for people and must not be parsed as a machine contract. A completed test failure can still produce a valid JUnit artifact; an infrastructure failure may produce none.

check-config checks common JSON shape, registration currentness, and registered profile selection. It does not load the profile or validate profile-owned values and operational targets. Those checks occur during run.

Execute the starters with PowerShell. Exit code 1 indicates a completed run with failed test evidence. The CLI removes an existing JUnit file only when run executes; a failed preflight never reaches that removal. Each starter therefore writes and publishes within the current job's directory rather than collecting earlier jobs' artifacts.

The GitLab CI, GitHub Actions, Jenkins, and TeamCity starters include project-level serialization. For Azure Pipelines, use one usable parallel slot or an equivalent exclusive-resource mechanism. Project-level locks alone do not protect a runtime shared by several repositories; agent provisioning must prevent those concurrent jobs too.

Runtime intent and startup

Use configuration schema 2 with explicit runtime.provisioningMode set to UseExisting for an existing runtime. Omission means CreateOwned, including for legacy schema-1 files. Unsupported creation or managed project operations fail rather than switching modes. Runtime reuse still performs the CLI's project build and transfer; required target values and project-source restrictions belong to the profile configuration guide.

The CLI waits for observed RunControl Idle + Ready before requesting UnitTest Start. The default initial deadline is 10 seconds after communication and monitoring are active. --unittest-ready-timeout <seconds> changes it using positive whole seconds. These are CLI options, not JSON configuration fields or WPF settings.

Timeout normally exits with code 31 and bounded cleanup. --reset-on-startup-timeout explicitly enables one gated Reset after that deadline; the starters leave it disabled. Accepted Reset must be followed by Idle + Ready within execution.timeouts.unitTestCommandReaction (default 10 seconds). Explicit RunControl initialization errors or workflow failure stop without this recovery. There is no retry loop or automatic EventBuffer reset. A timeout does not prove that resetting the PLC is safe.

Optional evidence analysis

Add --analysis-output <directory> to run to retain an analysis package on failure. This includes failed tests, execution errors, timeout, cancellation and cleanup failure. Add --analysis-on always to include successful runs. Without an output directory, no analysis is exported. These options are specific to the CLI, not WPF settings or JSON configuration fields.

$jobResults = Join-Path "C:\ci\results" ([Guid]::NewGuid().ToString("N"))
PLCSIM.UnitTest.App.Cli.exe run --file C:\ci\unittest.json --output (Join-Path $jobResults 'junit.xml') --analysis-output (Join-Path $jobResults 'analysis')

Publish only the directory selected for this invocation. In a CI starter, use its job/build-attempt directory and matching publication rules instead.

The CLI selects exactly one report: Run Analysis when a RunEpoch exists (including partial runs); otherwise PLC Lifecycle Analysis for the latest requested PLC Start, Reset or UnitTest Start; otherwise Communication Health Analysis when trace evidence exists. A lifecycle command need not have been accepted or produced a response. Missing required evidence is reported explicitly without generating an empty package.

Each export uses a unique analysis-<UTC timestamp>-<unique id> subdirectory below the current job's analysis directory, containing run.zip, lifecycle.zip, or communication-health.zip. As with WPF analysis exports, the ZIP contains analysis.md, events.ndjson, and hierarchy.json where applicable. Read the summary first; keep the full package for investigating PLC-framework usage problems.

The shipped starters enable failure-only export and collect ZIPs recursively even after a failed run. Use a clean or job-specific artifact directory: previous analysis packages are not deleted. A successful run normally has no ZIP; a separate configuration preflight failure does not execute run and cannot create one either.

Analysis is captured before cleanup and written afterwards. It does not include cleanup evidence. Export errors appear on stderr without changing the test result, JUnit or primary exit code. Collection uses the bounded activity trace, requires no raw-event logging or extra PLC interaction, and may contain incomplete evidence. ZIP writing has an independent cooperative 10-second deadline. Forced termination or a permanently hung process cannot guarantee an export.

If coordinated cleanup fails, its exit code 50 takes precedence over the earlier run outcome. Cleanup failure can trigger export of captured evidence, but its cause must be investigated in the job/application log.

Protect diagnostic artifacts. PLC payloads, assertion values, names, paths and diagnostic details can be sensitive. Restrict access and retention in CI and review packages before sharing them externally.

Configuration and diagnostics

Keep configuration files as protected CI inputs when they contain credentials. Prefer immutable project archives over direct engineering projects for unattended runs. The CLI performs bounded cleanup, but forced process or agent termination can still require manual runtime inspection before the next job.

For failed infrastructure runs, retain the job log first. Access-profile logs from %LOCALAPPDATA%\PLCSIM.UnitTest\logs can be collected as restricted, short-lived diagnostic artifacts when required.

Do not print configurations containing credentials or pass credentials as command-line arguments. Review shared log directories before publishing them; they may contain unrelated activity from the same Windows account.

Output and publication paths use CI_JOB_ID for GitLab CI, github.run_id plus github.run_attempt for GitHub, BUILD_NUMBER for Jenkins, Build.BuildId plus System.JobAttempt for Azure, and teamcity.build.id for TeamCity. Keep both paths aligned when adapting the starters. Multiple jobs, configurations, or repeated CLI invocations need separate result directories too.

In the default installation, these files are below C:\Program Files\PLCSIM.UnitTest\Examples\CI. Profile configuration is documented at profiles\<profile package>\docs\configuration.md below the installation root; additional vendor setup and usage documentation lives with that profile. The starters contain pipeline examples, not vendor-independent runnable project configurations.

Starting points, not turnkey pipelines. Adapt paths, configuration, output locations, runner labels, agent capabilities, credentials, and vendor-specific preparation to the target environment.
